    70→    70→2.  The Strategic Pivot
    71→    71→The existing blueprint positions DenialDefender as "the agent that fights your insurance company for you" and, operationally, as "AI that writes insurance appeal letters." That framing is emotionally resonant but technically dangerous: it invites the judge to evaluate the project as a letter generator, in which case a single hallucinated citation or an unverified claim collapses the entire submission. The pivot is to re-position the product one level up the abstraction stack, from output to workflow.

    96→    96→3.  Three Fatal Weaknesses of “Build-As-Written”
    97→    97→The reviewer's forensics on the existing blueprint converge on three failure modes that, left uncorrected, would cap the project at a strong track prize rather than the Grand Prize. Each is stated here as a steel-manned objection so that the engineering plan in Parts IV and V can be read as direct responses.
    98→    98→Weakness 1 — The Outcome-Learning gimmick (severity: critical)
    99→    99→The blueprint's self-evolving moment is a procedural-evidence weight changing from 0.42 to 0.48. Visually this is excellent, but a sophisticated judge can ask, "So you changed a number. How do you know the system actually improved?" Without an experimental answer, the most agentic claim in the entire submission collapses into a UI animation. The fix is to convert Outcome Learning from a performed weight-change into a measured before/after evaluation across a held-out case set, demonstrated live on two cases where the ranking of arguments visibly changes because of recorded outcomes. This single change converts the project from "an agent that changes its weights" into "a system whose behavior changed because of validated outcomes" — the latter is genuinely agentic; the former is theater.
   100→   100→Weakness 2 — Synthetic-only data leaves no credibility floor (severity: high)
   101→   101→A demo built entirely on synthetic denial letters, synthetic medical records, and a synthetic outcome corpus has no defensible answer to "where does your medical knowledge come from?" The answer "we generated it" is exactly the answer that triggers hallucination concerns. The fix is to anchor the evidence corpus in authoritative public sources — CMS denial reason statements and eMDR codes, CMS public-use claims files, CMS SynPUFs (which CMS explicitly created so developers can work with realistic Medicare claims structures while protecting beneficiary privacy), official Medicare appeals guidance, and versioned, frozen payer medical-policy documents. CMS itself distinguishes public-use files from identifiable data and states that public-use files do not contain PHI or PII requiring a data-use agreement, which gives the project a clean, citable data story.
   102→   102→Weakness 3 — The "Google product parade" dilutes reliability (severity: high)
   103→   103→The blueprint is committed to all seven Google Enterprise Agent Platform (GEAP) components plus Gemma, Veo, Lyria, A2A, and MCP. The official rules require only Gemini plus one Google agent framework plus one Google Cloud infrastructure service; the GEAP components are recommended for the Fleet track, not each individually mandatory. Shipping seven labels at the cost of reliability produces a demo in which no single integration is undeniably excellent and several are stubbed — exactly the failure pattern the blueprint's own kill-your-darlings philosophy warns against. The fix is ruthless trimming: keep the core (ADK, Cloud Run, Firestore, Cloud SQL pgvector, Pub/Sub) and the governance trio (Model Armor, Agent Identity, Agent Observability); treat Memory Bank, Gateway, Registry, Veo, Lyria, A2A, and MCP as conditional additions that survive only if they demonstrably strengthen the narrative without compromising the demo.

   111→   111→5.  The Triad Architecture (Evidence · Agents · Governance)
   112→   112→The judging architecture a judge should see at the end of the demo is a triad: Evidence, Agents, and Governance, joined at a human-approval vertex, leading to an appeal package, an outcome, and measured learning. This is deliberately not a diagram of "eight agents" or a "Google stack" — those are implementation details that sit inside the Agents vertex. The triad is the product; everything else is plumbing in service of it. The discipline of drawing the architecture this way forces every component to justify itself against one of the three vertices or the outcome loop, and it makes the multi-agent necessity argument visual rather than rhetorical.

   139→   139→Three architectural consequences follow from the triad. First, the Evidence vertex is a first-class subsystem with its own storage, versioning, and provenance — not a vector index bolted onto the agents. Second, the Agents vertex is internally a workflow orchestrated by ADK, but externally it presents as a single decision-trace stream, so judges never have to reason about agent topology to understand a case. Third, the Governance vertex is co-equal with the other two: PHI Guard, Model Armor, Agent Identity, and Agent Observability are not security afterthoughts tacked onto a working pipeline — they are the third pillar of the product, and the PHI Guard in particular is a demo-grade feature, not a backend detail.
   140→   140→Why a triad and not a stack
   141→   141→A stack diagram invites the judge to ask "why so many boxes?" A triad invites the judge to ask "is each pillar genuinely necessary?" — which is the question the project can actually answer. Removing Evidence breaks citation grounding; removing Agents breaks the workflow and the multi-agent necessity argument; removing Governance breaks the enterprise-grade and production-readiness criteria. The triad is therefore the minimum architecture that satisfies all three judging dimensions simultaneously, which is why it is the headline diagram rather than the agent graph.
   142→   142→6.  Agent Architecture — Eight Genuinely Necessary Specialists
   143→   143→Eight specialized agents implement the workflow. The headline is not "eight agents" — it is "a verified appeal workflow that learns from outcomes, implemented by eight specialists." A sophisticated judge does not care whether the count is 8, 12, or 34; they care why these boundaries are necessary. The table below is the one-screen architecture justification: each agent, its single responsibility, and what measurably breaks if it is removed. This table is also the basis of the ablation experiment in Section 7.
   144→   144→Table 6.1 — The eight agents. Each row is a necessity argument; Section 7 turns it into a measured ablation.
   145→   145→
   146→   146→The agents are orchestrated by the Agent Development Kit (ADK), Google's open-source framework for building, debugging, and deploying reliable AI agents at enterprise scale. ADK provides the delegation, hand-off, and tool-calling primitives that make the eight-agent topology a workflow rather than eight independent prompts. Agents persist case context to Firestore and long-term memory to Vertex AI Memory Bank (where stable), so the system exhibits genuine persistent context — a criterion the Fortified Enterprise Fleet track explicitly rewards. Each agent emits structured decision-trace events to a Pub/Sub topic consumed by the Agent Observability sink, so the demo's decision trace is not a separate instrumentation layer but a first-class output of the orchestration.
   147→   147→Why eight and not fewer  The ablation in Section 7 is designed to show that a single agent cannot ground citations independently and verify them in the same pass (incentive conflict), and that collapsing Policy Research and Evidence Assembly into one agent destroys the citation/clinical-evidence distinction the appeal depends on. The count is justified by measurement, not by ambition.
   148→   148→7.  Necessity Justification & the Agent-Ablation Experiment

A narrative answer is weak; a measured answer is decisive. The agent-ablation experiment is therefore a killer technical artifact: run the same held-out case set through progressively richer agent topologies and measure the property each agent is supposed to protect. The numbers below are targets to be measured, not claims; the experiment must demonstrate that multi-agent separation improves something measurable, and the result is reported whether or not it flatters the architecture.

   186→   186→9.  Provenance & Citation Architecture
   187→   187→Provenance is elevated from a backend detail to a core product feature. Every important claim in an appeal carries a provenance card the judge can open with one click, which directly attacks the hallucination concern that sinks most LLM-in-healthcare submissions. The provenance record is a structured object, not a free-text citation, so it is machine-checkable by the Quality Review agent and human-checkable by the judge in seconds. This is the single most cost-effective credibility upgrade in the entire plan: it costs roughly one day of engineering (Day 5) and lifts the Innovation and Architecture scores simultaneously.

   197→   197→Three properties make the provenance system credible rather than decorative. First, every evidence document is content-hashed at ingestion, so the version used at appeal time is the version on disk — a judge can verify the hash. Second, effective dates are mandatory; an appeal never cites a clause whose effective date has lapsed, because the Compliance agent rejects it. Third, the provenance status field is one of a controlled set (verified, retrieved, model-generated, synthetic), so the UI can color-code trust and the Quality Review agent can refuse to pass a draft whose citations are not all verified or retrieved. This is what makes the “5 citations checked → 5 verified” demo moment truthful rather than aspirational.
   198→   198→10.  Security & Governance Architecture — PHI Guard
   199→   199→The governance vertex of the triad is built from four components: PHI Guard, Model Armor, Agent Identity, and Agent Observability. PHI Guard is the demo-grade feature; the other three are the enterprise-governance proof. PHI Guard sits in front of the agent fleet and classifies every upload before any model invocation: synthetic or public content is allowed through; potential PHI is blocked and the block is logged. The decisive property is that a block means no model invocation occurred — which is both a real security guarantee and an excellent enterprise-security demo moment.
   200→   200→Figure 10.1 — PHI Guard. A block guarantees zero model invocation, which is the security wow moment.
   201→   201→Upload
   202→   202→  |
   203→   203→  v
   204→   204→PHI Guard  (classifier: is this potential PHI?)
   205→   205→  +-- Synthetic / Public  --> ALLOW  --> agent fleet
   206→   206→  +-- Potential PHI       --> BLOCK   --> no model invocation, logged
   207→   207→The demo uses PHI Guard twice. The first upload is a synthetic case, and the banner reads “No PHI detected — processing allowed.” The second upload is a deliberately constructed sensitive document, and the banner reads “Potential PHI detected — processing blocked. No model invocation occurred.” That contrast is the security wow and it is truthful because the classifier runs before any agent. Model Armor is then wired as the second layer inside the agent fleet for prompt-injection and jailbreak defense on retrieved content, Agent Identity scopes each agent's permissions so the Quality Review agent cannot write appeals and the Letter Drafting agent cannot ingest outcomes, and Agent Observability sinks the decision-trace Pub/Sub stream into a queryable store so every case is auditable end-to-end. Together these four satisfy the enterprise-governance criterion the Fleet track rewards.
   208→   208→The HIPAA language fix (non-negotiable)  Remove the sentence “HIPAA does not apply to the demo or repo.” It is unnecessarily categorical and invites attack. Replace it with: “The hackathon prototype is intentionally designed not to process PHI. Demonstration cases are synthetic and public sources are non-PHI. We are not claiming production HIPAA compliance. A production deployment handling PHI would require the applicable HIPAA privacy/security program, contractual arrangements, access controls, auditability, and governance.” HHS's official guidance describes formal de-identification through Safe Harbor or Expert Determination; the replacement language is almost impossible to attack without arguing against an explicit scope.
   209→   209→11.  Memory & State Architecture
   210→   210→Persistent context is an explicit Fortified Enterprise Fleet criterion, so memory is engineered, not improvised. Three tiers are kept and two are dropped, because complexity must appear only where the judge can see its payoff. The tiers that survive each have a visible demo consequence; the tiers that are cut have no visible payoff and would only add failure surface.
   211→   211→Table 11.1 — Memory tiers. Three kept (each with a demo payoff), two cut (no payoff, only failure surface).
   212→   212→
   213→   213→The case state machine is the backbone of the workflow. A case moves through states — intake, triaged, researched, drafted, verified, approved, submitted, outcome-recorded, learned — and each transition is a Firestore write that emits a decision-trace event. The HITL gates are explicit states, not interruptions: Gate 1 (confirm extracted denial information) sits between triaged and researched; Gate 2 (approve or edit the appeal) sits between verified and submitted. The Memory Bank stores the procedural-evidence weights that Outcome Learning updates, which is what makes the second-case ranking change a real state transition rather than a recompute. This tiering is what "persistent context" means in practice: a case resumed three days later opens at exactly the state it was left in, with its decision trace intact.

   222→   222→13.  The Outcome-Learning Experiment (Measured, Not Performed)
   223→   223→This is the most important technical recommendation in the entire document and the single biggest strategic change from the blueprint as written. Outcome Learning must be converted from a performed weight-change animation into a measured before/after evaluation demonstrated live across two cases. The blueprint's target of at least 20% improvement in top-3 retrieval is kept, but it must be measured before it is claimed. A judge can always ask “how do you know the system improved?” — the only defensible answer is an experiment.
   224→   224→Experimental design
   225→   225→The learning corpus is built from three legitimate sources: public authoritative evidence, public appeal-decision material, and synthetic controlled cases — not “50 fake wins.” CMS's public appeals materials demonstrate that the appeal process is multi-stage and outcome-oriented, which gives the corpus a defensible outcome signal. The evaluation harness runs as follows: fifty synthetic training outcomes are ingested; weights are updated; the same ten held-out cases are scored before and after. Five metrics are measured — top-1 retrieval accuracy, top-3 retrieval accuracy, citation grounding, argument selection, and appeal quality. The result is reported whether or not it flatters the system, because an honest negative result is more credible than an inflated positive one.

   238→   238→  -> score again
   239→   239→  -> diff metrics   (target: top-3 retrieval +>=20%)
   240→   240→The two-case live demonstration
   241→   241→The measured experiment is the technical artifact; the two-case live demonstration is the demo artifact. Case 1 runs to a LOSS, the system updates procedural evidence, and Case 2 — same payer, related denial — runs with a visibly different argument ranking, which the agent explains: “This ranking changed because two previous validated outcomes favored Argument C.” That is actual observable learning. A judge understands it instantly, and it is vastly stronger than a green “+0.06.” The before/after metric (“Top-3 retrieval accuracy: 60% → 80%”) is shown only if it was actually measured; an unmeasured number is never displayed.
   242→   242→14.  Decision Trace — Not “Agent Thoughts”
   243→   243→The blueprint repeatedly says “every agent's thoughts visible.” That phrasing is technically and conceptually dangerous. Exposing private chain-of-thought invites the judge to evaluate the reasoning process rather than the decision, and it pretends to expose hidden reasoning that the model does not actually expose faithfully. The replacement is a structured decision trace: discrete, named, verifiable events emitted by each agent as it completes a step. This gives judges transparency without pretending to expose hidden reasoning, and it is safer conceptually because the trace is a record of decisions, not a confession of internal monologue.

   262→   262→The Quality Review agent is strengthened from a passive “does this look good?” checker into an explicit adversarial agent whose job is to break the draft before a human ever sees it.    301→   301→21.  The Evaluation Harness — Experimental Backbone
   302→   302→The evaluation harness is the most important engineering artifact in the submission, because it produces the two strongest technical artifacts — the agent ablation (Section 7) and the outcome-learning before/after (Section 13) — from a single set of held-out cases. It is built as the eval Cloud Run service and is run nightly so that a regression in any metric is visible before it reaches the demo. The harness is deterministic: the same case set and the same model configuration produce the same scores, so before/after deltas are attributable to the learning update rather than to model non-determinism. Temperature is pinned to zero for evaluation runs; only the live demo uses a slightly higher temperature for narrative quality.
   303→   303→Held-out case set
   304→   304→Ten held-out cases are reserved and never used for weight updates. They are constructed to span the denial categories the triage classifier must distinguish (medical necessity, coding, prior authorization, experimental, out-of-network, other) and to include at least one case per primary payer in the corpus. The same ten cases are scored before learning, after learning, and across each ablation topology, which means one harness run produces the evidence for both killer artifacts. The case set is checked into the repo under data/cases/held_out/ and is versioned; any change to it is a commit that must be justified, because silently altering the held-out set is the easiest way to invalidate every metric in the submission.

   384→   384→36.  Counterarguments & Responses (Steelmanned)
   385→   385→A strong submission pre-empts its own objections. Five counterarguments are steelmanned below — each is made as strong as possible before the response is given, so that the responses survive a skeptical judge rather than a friendly one. The pattern for each is: state the objection at full strength, concede what is true, define the limits, and explain why the doctrine in Part I still holds.
   386→   386→Counterargument 1 — Synthetic cases mean the system is unproven on real denials.
   387→   387→Steel-man: a demo on synthetic data does not prove the system works on real payer letters, so the operational-utility claim is unsupported. Concession: the cases are indeed synthetic, and the system is not claimed to be production-validated. Limit and response: the institutional knowledge is not synthetic — it is sourced from CMS and payer public material, versioned and hashed, with provenance cards the judge can verify. The Triage agent classifies against CMS's published denial-reason statements, not free text. The domain-validation panel records a specialist's concrete changes. So the claim is scoped: evidence-backed appeal draft on synthetic cases grounded in real public evidence, not proven on real denials. The doctrine holds because the scope is explicit and defensible, not overclaimed.
   388→   388→Counterargument 2 — Eight agents is over-engineered; three would do.
   389→   389→Steel-man: most denial-appeal work is triage, draft, review, so eight agents is theater. Concession: a three-agent pipeline can produce a draft. Limit and response: the ablation table (Section 7) is measured, not asserted, and is designed to show that each removed agent reintroduces a measurable failure — collapsing Policy Research and Evidence Assembly destroys the citation/clinical-evidence distinction; removing Quality Review reintroduces unsupported claims the compliance story cannot tolerate. The count is justified by measurement; if the ablation does not show a marginal lift per agent, the doctrine requires reporting the honest result, and the agent is a candidate for Kill-Your-Darlings. The doctrine holds because the necessity argument is empirical, not rhetorical.
   390→   390→Counterargument 3 — The outcome-learning result could be a measured negative.
   391→   391→Steel-man: if fifty outcomes do not move top-3 retrieval by 20 percent, the headline agentic claim fails. Concession: this is a real risk and the experiment might not flatter the system. Limit and response: Principle 5 (honest negative results are acceptable) is explicit that a measured non-improvement is reported, not hidden — and a credible negative result with a sound experiment is far stronger than an inflated positive claim a judge can debunk in thirty seconds. Even a modest positive delta, honestly measured and shown live across two cases, is a stronger agentic artifact than any animation. The doctrine holds because credibility is the objective, not a specific number.
   392→   392→Counterargument 4 — The Google stack is still too broad; something will be stubbed.
   393→   393→Steel-man: even the trimmed stack (Table 12.1) is a lot for 14 days, and a stubbed integration is worse than none. Concession: the risk is real; some optional components may not survive. Limit and response: the stack is tiered, and every component below the Core and Governance tiers is conditional on a gate that asks whether it strengthens the narrative without compromising the demo. The blueprint's own Gate 2 rule (if a GEAP component has to be stubbed, trim it and document why) is applied ruthlessly, and the demo never depends on a component that is not reliably working. The doctrine holds because reliability outranks labels (Principle 4).
   394→   394→Counterargument 5 — No real payer integration means this is not operational.
   395→   395→Steel-man: without a real payer channel, the system cannot actually submit an appeal, so operational-utility is theoretical. Concession: the system does not submit to payers, by design. Limit and response: the blueprint's kill-your-darlings list (no payer portals, fax, email, EHR, live scraping, real PHI, blockchain, Kubernetes) is accepted in full, because the cost of a flaky payer integration in a 14-day demo exceeds its value. The operational utility is the human's: a 6-hour ordeal becomes a 90-second draft with verifiable evidence, which the human then submits through the existing channel. The NPI Registry is the one legitimate external lookup that proves the system can act on real public data. The doctrine holds because the value proposition is human throughput, not autonomous submission.
