    97→2.  The Strategic Pivot
    98→The existing blueprint positions DenialDefender as "the agent that fights your insurance company for you" and, operationally, as "AI that writes insurance appeal letters." That framing is emotionally resonant but technically dangerous: it invites the judge to evaluate the project as a letter generator, in which case a single hallucinated citation or an unverified claim collapses the entire submission. The pivot is to re-position the product one level up the abstraction stack, from output to workflow.
    99→The new target identity is evidence-grounded, human-governed autonomous denial-appeal operations. The central loop is no longer "upload denial → produce letter" but a ten-stage closed loop in which the letter is merely the most visible intermediate artifact and the outcome is the thing the system actually optimizes for:
   100→Figure 2.1 — The ten-stage closed loop. The appeal letter is an intermediate artifact, not the deliverable; the deliverable is a workflow that measurably improves.

   103→3.  Three Fatal Weaknesses of “Build-As-Written”
   104→The reviewer's forensics on the existing blueprint converge on three failure modes that, left uncorrected, would cap the project at a strong track prize rather than the Grand Prize. Each is stated here as a steel-manned objection so that the engineering plan in Parts IV and V can be read as direct responses.
   105→Weakness 1 — The Outcome-Learning gimmick (severity: critical)
   106→The blueprint's self-evolving moment is a procedural-evidence weight changing from 0.42 to 0.48. Visually this is excellent, but a sophisticated judge can ask, "So you changed a number. How do you know the system actually improved?" Without an experimental answer, the most agentic claim in the entire submission collapses into a UI animation. The fix is to convert Outcome Learning from a performed weight-change into a measured before/after evaluation across a held-out case set, demonstrated live on two cases where the ranking of arguments visibly changes because of recorded outcomes. This single change converts the project from "an agent that changes its weights" into "a system whose behavior changed because of validated outcomes" — the latter is genuinely agentic; the former is theater.
   107→Weakness 2 — Synthetic-only data leaves no credibility floor (severity: high)
   108→A demo built entirely on synthetic denial letters, synthetic medical records, and a synthetic outcome corpus has no defensible answer to "where does your medical knowledge come from?" The answer "we generated it" is exactly the answer that triggers hallucination concerns. The fix is to anchor the evidence corpus in authoritative public sources — CMS denial reason statements and eMDR codes, CMS public-use claims files, CMS SynPUFs (which CMS explicitly created so developers can work with realistic Medicare claims structures while protecting beneficiary privacy), official Medicare appeals guidance, and versioned, frozen payer medical-policy documents. CMS itself distinguishes public-use files from identifiable data and states that public-use files do not contain PHI or PII requiring a data-use agreement, which gives the project a clean, citable data story.
   109→Weakness 3 — The "Google product parade" dilutes reliability (severity: high)
   110→The blueprint is committed to all seven Google Enterprise Agent Platform (GEAP) components plus Gemma, Veo, Lyria, A2A, and MCP. The official rules require only Gemini plus one Google agent framework plus one Google Cloud infrastructure service; the GEAP components are recommended for the Fleet track, not each individually mandatory. Shipping seven labels at the cost of reliability produces a demo in which no single integration is undeniably excellent and several are stubbed — exactly the failure pattern the blueprint's own kill-your-darlings philosophy warns against. The fix is ruthless trimming: keep the core (ADK, Cloud Run, Firestore, Cloud SQL pgvector, Pub/Sub) and the governance trio (Model Armor, Agent Identity, Agent Observability); treat Memory Bank, Gateway, Registry, Veo, Lyria, A2A, and MCP as conditional additions that survive only if they demonstrably strengthen the narrative without compromising the demo.

   158→5.  The Triad Architecture (Evidence · Agents · Governance)
   159→The judging architecture a judge should see at the end of the demo is a triad: Evidence, Agents, and Governance, joined at a human-approval vertex, leading to an appeal package, an outcome, and measured learning. This is deliberately not a diagram of "eight agents" or a "Google stack" — those are implementation details that sit inside the Agents vertex. The triad is the product; everything else is plumbing in service of it. The discipline of drawing the architecture this way forces every component to justify itself against one of the three vertices or the outcome loop, and it makes the multi-agent necessity argument visual rather than rhetorical.
   160→Figure 5.1 — The judging triad. The product is the loop, not the agent count or the stack.
   161→                 DENIALDEFENDER                       |        +--------------+--------------+        |              |              |    EVIDENCE        AGENTS       GOVERNANCE        |              |              | CMS / payer       8 specialists   PHI Guard public sources    ADK workflow    Model Armor        |              |          Identity        |              |          Observability        +--------------+--------------+                       |                 HUMAN APPROVAL                       |                       v              APPEAL PACKAGE                       |                       v                   OUTCOME                       |                       v             MEASURED LEARNING                       |                       v                BETTER NEXT CASE
   162→Three architectural consequences follow from the triad. First, the Evidence vertex is a first-class subsystem with its own storage, versioning, and provenance — not a vector index bolted onto the agents. Second, the Agents vertex is internally a workflow orchestrated by ADK, but externally it presents as a single decision-trace stream, so judges never have to reason about agent topology to understand a case. Third, the Governance vertex is co-equal with the other two: PHI Guard, Model Armor, Agent Identity, and Agent Observability are not security afterthoughts tacked onto a working pipeline — they are the third pillar of the product, and the PHI Guard in particular is a demo-grade feature, not a backend detail.
   163→Why a triad and not a stack
   164→A stack diagram invites the judge to ask "why so many boxes?" A triad invites the judge to ask "is each pillar genuinely necessary?" — which is the question the project can actually answer. Removing Evidence breaks citation grounding; removing Agents breaks the workflow and the multi-agent necessity argument; removing Governance breaks the enterprise-grade and production-readiness criteria. The triad is therefore the minimum architecture that satisfies all three judging dimensions simultaneously, which is why it is the headline diagram rather than the agent graph.

   230→8.  Data & Evidence Architecture — Real Public Evidence + Synthetic Cases
   231→The data architecture is the project's credibility floor and its single most important upgrade over the blueprint as written. The principle is absolute: patient cases are synthetic by design; the institutional knowledge grounding them is real and authoritative. This split is what converts "our data is synthetic" (a confession) into "our cases are synthetic by design, and the healthcare knowledge is sourced from authoritative public payer and government material" (a credibility statement). The architecture below implements that split as three versioned layers feeding one evidence corpus.

   262→9.  Provenance & Citation Architecture
   263→Provenance is elevated from a backend detail to a core product feature. Every important claim in an appeal carries a provenance card the judge can open with one click, which directly attacks the hallucination concern that sinks most LLM-in-healthcare submissions. The provenance record is a structured object, not a free-text citation, so it is machine-checkable by the Quality Review agent and human-checkable by the judge in seconds. This is the single most cost-effective credibility upgrade in the entire plan: it costs roughly one day of engineering (Day 5) and lifts the Innovation and Architecture scores simultaneously.
   264→Figure 9.1 — The provenance card. Every citation in an appeal resolves to one of these; the judge clicks “Why did the agent say this?” and gets this.
   265→SOURCE          CMS / PAYERDOCUMENT        Medical Policy XSECTION         4.2EFFECTIVE DATE  2026-01-01RETRIEVED       2026-08-15PROVENANCE      AUTHORITATIVE / PUBLICSTATUS          VERIFIEDCONTENT HASH    sha256:9f2c...e1a
   266→Three properties make the provenance system credible rather than decorative. First, every evidence document is content-hashed at ingestion, so the version used at appeal time is the version on disk — a judge can verify the hash. Second, effective dates are mandatory; an appeal never cites a clause whose effective date has lapsed, because the Compliance agent rejects it. Third, the provenance status field is one of a controlled set (verified, retrieved, model-generated, synthetic), so the UI can color-code trust and the Quality Review agent can refuse to pass a draft whose citations are not all verified or retrieved. This is what makes the “5 citations checked → 5 verified” demo moment truthful rather than aspirational.
   267→10.  Security & Governance Architecture — PHI Guard
   268→The governance vertex of the triad is built from four components: PHI Guard, Model Armor, Agent Identity, and Agent Observability. PHI Guard is the demo-grade feature; the other three are the enterprise-governance proof. PHI Guard sits in front of the agent fleet and classifies every upload before any model invocation: synthetic or public content is allowed through; potential PHI is blocked and the block is logged. The decisive property is that a block means no model invocation occurred — which is both a real security guarantee and an excellent enterprise-security demo moment.
   269→Figure 10.1 — PHI Guard. A block guarantees zero model invocation, which is the security wow moment.
   270→Upload  |  vPHI Guard  (classifier: is this potential PHI?)  +-- Synthetic / Public  --> ALLOW  --> agent fleet  +-- Potential PHI       --> BLOCK   --> no model invocation, logged
   271→The demo uses PHI Guard twice. The first upload is a synthetic case, and the banner reads “No PHI detected — processing allowed.” The second upload is a deliberately constructed sensitive document, and the banner reads “Potential PHI detected — processing blocked. No model invocation occurred.” That contrast is the security wow and it is truthful because the classifier runs before any agent. Model Armor is then wired as the second layer inside the agent fleet for prompt-injection and jailbreak defense on retrieved content, Agent Identity scopes each agent's permissions so the Quality Review agent cannot write appeals and the Letter Drafting agent cannot ingest outcomes, and Agent Observability sinks the decision-trace Pub/Sub stream into a queryable store so every case is auditable end-to-end. Together these four satisfy the enterprise-governance criterion the Fleet track rewards.
   272→The HIPAA language fix (non-negotiable)  Remove the sentence “HIPAA does not apply to the demo or repo.” It is unnecessarily categorical and invites attack. Replace it with: “The hackathon prototype is intentionally designed not to process PHI. Demonstration cases are synthetic and public sources are non-PHI. We are not claiming production HIPAA compliance. A production deployment handling PHI would require the applicable HIPAA privacy/security program, contractual arrangements, access controls, auditability, and governance.” HHS's official guidance describes formal de-identification through Safe Harbor or Expert Determination; the replacement language is almost impossible to attack without arguing against an explicit scope.

   371→13.  The Outcome-Learning Experiment (Measured, Not Performed)
   372→This is the most important technical recommendation in the entire document and the single biggest strategic change from the blueprint as written. Outcome Learning must be converted from a performed weight-change animation into a measured before/after evaluation demonstrated live across two cases. The blueprint's target of at least 20% improvement in top-3 retrieval is kept, but it must be measured before it is claimed. A judge can always ask “how do you know the system improved?” — the only defensible answer is an experiment.
   373→Experimental design
   374→The learning corpus is built from three legitimate sources: public authoritative evidence, public appeal-decision material, and synthetic controlled cases — not “50 fake wins.” CMS's public appeals materials demonstrate that the appeal process is multi-stage and outcome-oriented, which gives the corpus a defensible outcome signal. The evaluation harness runs as follows: fifty synthetic training outcomes are ingested; weights are updated; the same ten held-out cases are scored before and after. Five metrics are measured — top-1 retrieval accuracy, top-3 retrieval accuracy, citation grounding, argument selection, and appeal quality. The result is reported whether or not it flatters the system, because an honest negative result is more credible than an inflated positive one.
   375→Figure 13.1 — Before/after evaluation. The same ten cases, scored twice; the delta is the agentic claim.
   376→BEFORE LEARNING  -> retrieve top-3 arguments on 10 held-out cases  -> score (top-1 acc, top-3 acc, grounding, argument, quality)  -> snapshot metricsTHEN  -> ingest 50 outcome records (public + synthetic)  -> update procedural-evidence weightsAFTER LEARNING  -> run same 10 held-out cases  -> score again  -> diff metrics   (target: top-3 retrieval +>=20%)
   377→The two-case live demonstration
   378→The measured experiment is the technical artifact; the two-case live demonstration is the demo artifact. Case 1 runs to a LOSS, the system updates procedural evidence, and Case 2 — same payer, related denial — runs with a visibly different argument ranking, which the agent explains: “This ranking changed because two previous validated outcomes favored Argument C.” That is actual observable learning. A judge understands it instantly, and it is vastly stronger than a green “+0.06.” The before/after metric (“Top-3 retrieval accuracy: 60% → 80%”) is shown only if it was actually measured; an unmeasured number is never displayed.
   379→14.  Decision Trace — Not “Agent Thoughts”
   380→The blueprint repeatedly says “every agent's thoughts visible.” That phrasing is technically and conceptually dangerous. Exposing private chain-of-thought invites the judge to evaluate the reasoning process rather than the decision, and it pretends to expose hidden reasoning that the model does not actually expose faithfully. The replacement is a structured decision trace: discrete, named, verifiable events emitted by each agent as it completes a step. This gives judges transparency without pretending to expose hidden reasoning, and it is safer conceptually because the trace is a record of decisions, not a confession of internal monologue.
   381→Figure 14.1 — Decision trace. Structured, named, verifiable events; not chain-of-thought.
   382→Triage  [x] payer identified  [x] denial type classified  [x] deadline extractedPolicy Research  [x] 3 sources retrieved  [x] clause UNH-MN-014 selectedEvidence  [x] 4 supporting records foundQuality Review  [x] 5/5 citations verified  [x] 0 unsupported claims
   383→The decision trace is emitted to a Pub/Sub topic by each agent at step completion, persisted to Firestore as part of the case record, and rendered in the UI as a live event stream during the demo. Because each event is a structured object (agent, step, status, evidence references, timestamp), the Quality Review agent can read the trace to verify that every citation it later checks was actually retrieved by Policy Research — which closes the loop between trace and verification. This is what makes the trace an audit artifact rather than a decorative animation.
   384→15.  Adversarial Quality Review
   385→The Quality Review agent is strengthened from a passive “does this look good?” checker into an explicit adversarial agent whose job is to break the draft before a human ever sees it. It asks a fixed battery of attack questions and refuses to pass the draft until each is answered affirmatively. This turns the verification moment from a soft confirmation into a hard gate, and it is what makes the “5 citations checked → 5 verified” demo moment truthful: the verification is adversarial, not ceremonial.

   403→16.  External Integration Strategy — NPI Registry
   404→The system integrates exactly one legitimate external public API: the NPI Registry at npiregistry.cms.hhs.gov, a free public directory of all active National Provider Identifier records with a documented REST API (v2.1). When a synthetic case contains a provider, the Policy Research agent validates the provider's identity and taxonomy against the live NPI registry. This is the only place the demo can truthfully show “external public data lookup → agent decision,” which is far stronger than pretending Gemini itself is an “external action.” No payer portals, fax, email, EHR, live payer scraping, real PHI, blockchain, or Kubernetes are built — the blueprint's kill-your-darlings list is accepted in full.

   449→19.  Repository & Service Topology
   450→The repository is a monorepo with a small number of deployable Cloud Run services. A monorepo is chosen over a multi-repo split because the team is small (3–4 engineers), the build is short (14 days), and the cost of cross-repo coordination exceeds the cost of a slightly larger single repo. Each Cloud Run service has a single responsibility and scales independently, which satisfies the production-readiness criterion without introducing Kubernetes — the blueprint's kill of Kubernetes is accepted.

   452→denialdefender/                      (monorepo)  services/    api/           -> Cloud Run   (REST + WebSocket gateway, HITL, case state)    agents/        -> Cloud Run   (ADK-orchestrated 8-agent workflow)    ingest/        -> Cloud Run   (evidence corpus loader, hasher, versioner)    phi-guard/     -> Cloud Run   (upload classifier, blocks before invocation)    eval/          -> Cloud Run   (evaluation harness, ablation, before/after)  web/             -> Next.js    (decision trace UI, provenance cards, HITL gates)  packages/    shared-schema/ (pydantic / zod types)    provenance/    (citation + hash + effective-date)  data/    corpus/        (frozen, versioned CMS + payer sources)    cases/         (synthetic case definitions + held-out set)  infra/           (terraform / gcloud scripts, Cloud Run + Firestore + pgvector + Pub/Sub)
   453→The api service is the single entry point for the web client; it owns case state, HITL gate transitions, and the WebSocket channel that streams decision-trace events to the UI. The agents service hosts the ADK workflow and is invoked asynchronously via Pub/Sub so long-running cases do not block the gateway. The ingest service is a batch loader run once per evidence-corpus version; it hashes every document and writes provenance records to pgvector. The phi-guard service is deliberately separate so its block guarantee is auditable: a request that reaches the agents service provably passed the guard. The eval service is the experimental backbone described in Section 21.

   485→21.  The Evaluation Harness — Experimental Backbone
   486→The evaluation harness is the most important engineering artifact in the submission, because it produces the two strongest technical artifacts — the agent ablation (Section 7) and the outcome-learning before/after (Section 13) — from a single set of held-out cases. It is built as the eval Cloud Run service and is run nightly so that a regression in any metric is visible before it reaches the demo. The harness is deterministic: the same case set and the same model configuration produce the same scores, so before/after deltas are attributable to the learning update rather than to model non-determinism. Temperature is pinned to zero for evaluation runs; only the live demo uses a slightly higher temperature for narrative quality.
   487→Held-out case set
   488→Ten held-out cases are reserved and never used for weight updates. They are constructed to span the denial categories the triage classifier must distinguish (medical necessity, coding, prior authorization, experimental, out-of-network, other) and to include at least one case per primary payer in the corpus. The same ten cases are scored before learning, after learning, and across each ablation topology, which means one harness run produces the evidence for both killer artifacts. The case set is checked into the repo under data/cases/held_out/ and is versioned; any change to it is a commit that must be justified, because silently altering the held-out set is the easiest way to invalidate every metric in the submission.
   489→22.  Reliability & Demo-Failure Plan
   490→A demo that fails live is a submission that fails. The reliability plan assumes the live demo will encounter at least one degraded condition and engineers for it. Three paths guarantee the demo can always complete: a live path (the real system), a cached-rollback path (pre-recorded decision traces and drafts for the exact demo cases, replayed if latency or an error is detected), and a static-fallback path (a narrated walkthrough of the same artifacts if the network is unavailable). The operator can switch paths in under five seconds without the audience noticing, because all three render the same decision-trace and provenance UI.
