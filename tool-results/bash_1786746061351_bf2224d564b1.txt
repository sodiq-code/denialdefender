    [Normal] Weakness 2 — Synthetic-only data leaves no credibility floor (severity: high)
 >>>[Normal] A demo built entirely on synthetic denial letters, synthetic medical records, and a synthetic outcome corpus has no defensible answer to "where does your medical knowledge come from?" The answer "we generated it" is exactly the answer that triggers hallucination concerns. The fix is to anchor the evidence corpus in authoritative public sources — CMS denial reason statements and eMDR codes, CMS public-use claims files, CMS SynPUFs (which CMS explicitly created so developers can work with realistic Medicare claims structures while protecting beneficiary privacy), official Medicare appeals guidance, and versioned, frozen payer medical-policy documents. CMS itself distinguishes public-use files from identifiable data and states that public-use files do not contain PHI or PII requiring a data-use agreement, which gives the project a clean, citable data story.
    [Normal] Weakness 3 — The "Google product parade" dilutes reliability (severity: high)
    [Normal] The blueprint is committed to all seven Google Enterprise Agent Platform (GEAP) components plus Gemma, Veo, Lyria, A2A, and MCP. The official rules require only Gemini plus one Google agent framework plus one Google Cloud infrastructure service; the GEAP components are recommended for the Fleet track, not each individually mandatory. Shipping seven labels at the cost of reliability produces a demo in which no single integration is undeniably excellent and several are stubbed — exactly the failure pattern the blueprint's own kill-your-darlings philosophy warns against. The fix is ruthless trimming: keep the core (ADK, Cloud Run, Firestore, Cloud SQL pgvector, Pub/Sub) and the governance trio (Model Armor, Agent Identity, Agent Observability); treat Memory Bank, Gateway, Registry, Veo, Lyria, A2A, and MCP as conditional additions that survive only if they demonstrably strengthen the narrative without compromising the demo.
    [Normal] 4.  The Ultimate Doctrine — 13 Inviolable Principles

Every architectural, technical, and engineering decision in this document exists to deliver them, and every daily task in Part V is traceable to one or more of them. They are non-negotiable; if a planned feature cannot be mapped to at least one principle, it is cut.

    [Normal] 8.  Data & Evidence Architecture — Real Public Evidence + Synthetic Cases
 >>>[Normal] The data architecture is the project's credibility floor and its single most important upgrade over the blueprint as written. The principle is absolute: patient cases are synthetic by design; the institutional knowledge grounding them is real and authoritative. This split is what converts "our data is synthetic" (a confession) into "our cases are synthetic by design, and the healthcare knowledge is sourced from authoritative public payer and government material" (a credibility statement). The architecture below implements that split as three versioned layers feeding one evidence corpus.
    [Normal] Figure 8.1 — Public-data architecture. The corpus is versioned, hashed, and provenance-tagged; the patient case is synthetic.

   Synthetic patient case  -->  Real institutional evidence  -->  Evidence-backed appeal
    [Normal] Authoritative source inventory
    [Normal] The evidence corpus is built from named, citable public sources. CMS publishes standardized denial and non-affirmation reason statements used by Medicare review contractors, which gives the triage agent a controlled vocabulary rather than free-text classification. CMS publishes public-use Medicare claims files containing non-identifiable claim-specific information, and specifically created Medicare Claims Synthetic Public Use Files (SynPUFs) so developers can work with realistic Medicare claims structures while protecting beneficiary privacy. CMS and Medicare publicly document the multi-level appeal workflow. Publicly available payer medical-policy documents are used, but frozen and versioned for the hackathon — the system never scrapes payer portals live. CMS distinguishes public-use files from identifiable data and states that public-use files do not contain PHI or PII requiring a data-use agreement, which is the clean data story cited in the demo.
    [Normal] Table 8.1 — Evidence corpus source inventory. Each source is named, tiered, and frozen or versioned for the hackathon window.
    [Normal] Terminology discipline  Use six terms precisely and never interchangeably: synthetic (generated case), public-use (officially released non-identifiable dataset), de-identified (transformed per a de-identification standard), retrieved (external source pulled in), verified (human or deterministic check), and model-generated (AI output). The provenance architecture already distinguishes these categories; the discipline is to make the terminology visible in the UI and the Devpost copy.
    [Normal] 9.  Provenance & Citation Architecture
    [Normal] Provenance is elevated from a backend detail to a core product feature. Every important claim in an appeal carries a provenance card the judge can open with one click, which directly attacks the hallucination concern that sinks most LLM-in-healthcare submissions. The provenance record is a structured object, not a free-text citation, so it is machine-checkable by the Quality Review agent and human-checkable by the judge in seconds. This is the single most cost-effective credibility upgrade in the entire plan: it costs roughly one day of engineering (Day 5) and lifts the Innovation and Architecture scores simultaneously.

    [Normal] Upload
  |

PHI Guard  (classifier: is this potential PHI?)
  +-- Synthetic / Public  --> ALLOW  --> agent fleet

    [Normal] The demo uses PHI Guard twice. The first upload is a synthetic case, and the banner reads “No PHI detected — processing allowed.” The second upload is a deliberately constructed sensitive document, and the banner reads “Potential PHI detected — processing blocked. No model invocation occurred.” That contrast is the security wow and it is truthful because the classifier runs before any agent. Model Armor is then wired as the second layer inside the agent fleet for prompt-injection and jailbreak defense on retrieved content, Agent Identity scopes each agent's permissions so the Quality Review agent cannot write appeals and the Letter Drafting agent cannot ingest outcomes, and Agent Observability sinks the decision-trace Pub/Sub stream into a queryable store so every case is auditable end-to-end. Together these four satisfy the enterprise-governance criterion the Fleet track rewards.

A production deployment handling PHI would require the applicable HIPAA privacy/security program, contractual arrangements, access controls, auditability, and governance.” HHS's official guidance describes formal de-identification through Safe Harbor or Expert Determination; the replacement language is almost impossible to attack without arguing against an explicit scope.

Model Armor is then wired as the second layer inside the agent fleet for prompt-injection and jailbreak defense on retrieved content, Agent Identity scopes each agent's permissions so the Quality Review agent cannot write appeals and the Letter Drafting agent cannot ingest outcomes, and Agent Observability sinks the decision-trace Pub/Sub stream into a queryable store so every case is auditable end-to-end. Together these four satisfy the enterprise-governance criterion the Fleet track rewards.

We are not claiming production HIPAA compliance.     [Normal] Ten held-out cases are reserved and never used for weight updates.     [Normal] 31.  Daily Discipline — Standups, Risk Gates, Stopping Rules
    [Normal] A 14-day build with this many moving parts fails not from lack of talent but from lack of discipline. Three practices keep the build honest: a morning standup that confirms the day's gate, an evening standup that confirms the gate passed or a scope-cut was made, and a live-updating risk register that tracks every open issue against a day number.
