  3542→## 43.1 Technical Questions
  3543→
  3544→Q1. How do you handle the 1M-token context window — is that actually needed?
  3545→The 1M context is genuinely needed for the Letter Drafting Agent's final reasoning step, where the model holds the denial letter (5-10K tokens), the patient's medical records (50-200K tokens), the retrieved payer policy clauses (20-50K tokens), the applicable federal regulations (10-30K tokens), and the payer's submission requirements (5K tokens) simultaneously. Without 1M context, we'd have to chunk and lose cross-references between medical evidence and policy clauses. Gemini 3.5 Flash's 1M context is GA [B-1] and is the differentiator that makes this product possible in August 2026 and not before. Backup: Section 25 AI/ML Architecture; [B-1].
  3546→Q2. What's your end-to-end latency, and how do you stay under 90 seconds?
  3547→End-to-end is ~75-85 seconds in the live path. Denial Triage ~10s (multimodal Gemini call), Policy Research ~5s (pgvector HNSW query + Gemini reasoning), Evidence Assembly ~10s (parallel with Policy), Letter Drafting ~20s (Gemini + Gemma tone), Quality Review ~10s (Gemini validation), HITL gate is user-paced (~10s assumed), Deadline Tracker ~5s (deterministic computation). Total ~70s + buffer. The 90-second budget is enforced via hard per-call timeouts (30s) and the fallback path engages if any single call exceeds its budget. Backup: Section 28 Reliability; demo rehearsals log.
  3548→Q3. How do you scale beyond the demo?
  3549→Cloud Run autoscaling handles request volume; max-instances=10 for the demo, configurable up to 1000. The bottleneck is Gemini API quota, not Cloud Run — we'd negotiate higher quota with Google Cloud before scaling to clinic-tier volume (1000+ appeals/day). Cloud SQL pgvector HNSW handles 100K+ embeddings on db-g1-small; we'd upgrade to a larger instance at 1M+ embeddings. Firestore and Pub/Sub are serverless and scale automatically. Cost per appeal at scale drops to ~$0.10-0.20 (better token economics at volume). Backup: Section 29.10 Cost Optimization.
  3550→Q4. What's your cost per appeal?
  3551→~$0.10-0.50 per appeal in the live path, dominated by Gemini API calls (~$0.15 for ~100K input + 5K output tokens at Gemini 3.5 Flash pricing of $1.50/$9 per 1M [B-1]). Gemma adds ~$0.01, Veo adds $0.30 only if generated (1 in 5 appeals), Lyria adds $0.05 only if used. Cloud Run + Firestore + Pub/Sub + pgvector are sub-dollar at demo volume. At clinic-scale (1000 appeals/day), cost per appeal drops to ~$0.10. The $19/month B2C Pro tier covers ~40 appeals/month at $0.10 = $4 cost, ~80% margin. Backup: Section 29.10; Section 34.
  3552→Q5. How does the Outcome Learning Agent actually update weights?
  3553→When an outcome is recorded (win or loss), the Outcome Learning Agent ingests the case summary (payer, denial type, clauses cited, outcome), embeds it via Gemini text-embedding-005, stores it in the outcome_embeddings pgvector table, and updates the retrieval weight of each cited clause via a learning-rate-clamped update: new_weight = old_weight + learning_rate × (outcome_signal - expected_outcome). Learning rate is 0.1, clamped to prevent runaway updates. The weight delta is logged and surfaced in the UI — the "visible learning signal." Held-out evaluation shows ≥20% improvement in top-3 retrieval accuracy after 50 outcomes. Backup: Section 23 Memory / Learning Architecture; Section 34 Metrics.
