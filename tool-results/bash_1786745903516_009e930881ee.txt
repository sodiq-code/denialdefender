[Heading 2] 34.2 AI Component Evaluation Methodology
[Normal] The appeal letter is the central artifact; its quality is evaluated on a 5-dimension rubric adapted from the ADK evaluation framework [B-26]: (1) Factual accuracy — every statement of fact in the letter (payer policy clause, regulation citation, medical record reference) is verifiable against source documents; (2) Citation correctness — every cited clause exists and supports the claim being made; (3) Persuasive structure — the letter follows the canonical appeal-letter structure (intro → denial reason restatement → legal/policy basis → medical-necessity evidence → request for reconsideration → deadline reference); (4) Payer-format compliance — the letter meets the specific payer's submission requirements (length, format, required fields, submission channel); (5) Tone — professional, assertive, non-confrontational (the Gemma fine-tune's job). Each dimension scored 1-5 by Gemma-as-judge (calibrated against 10 human-scored reference letters); a human spot-checks 1 letter per demo rehearsal. Disagreement >1 point between Gemma and human triggers prompt iteration on the judge prompt.
[Normal] Citation accuracy and denial classification accuracy are evaluated deterministically. Citation accuracy: every cited clause ID in a drafted letter is looked up in pgvector; if found, the cited clause text is compared (semantic similarity >0.85) to the claim it's cited for. Denial classification accuracy: 50 synthetic denial letters are human-labeled with the expected denial type; the Denial Triage Agent is run on all 50; accuracy = correct / 50. The 50-letter test set is held out (not used in prompt development).
[Heading 2] 34.3 Outcome Learning Agent Improvement Measurement
[Normal] The Outcome Learning Agent's improvement is the hardest metric to measure in 14 days because real longitudinal outcome data doesn't exist yet. The measurement strategy has three components. Component 1 — Synthetic outcome corpus: 50 synthetic outcomes are pre-seeded, each labeled with payer × denial type × outcome (win/loss) × winning-clause-ID. The Outcome Learning Agent ingests these on Day 4; the before/after retrieval weights are logged. Component 2 — Visible weight delta: after ingesting a "win" outcome for a specific clause, the clause's retrieval weight must increase by ≥0.05 (clamped learning rate). This is the visible learning signal. Component 3 — Held-out evaluation: 10 held-out synthetic cases are run before and after Outcome Learning ingests the 50 outcomes; the held-out cases should retrieve the winning clauses more often after learning than before. Target: ≥20% improvement in top-3 retrieval accuracy on held-out cases. This is the canonical "self-evolving agent" claim made measurable — exactly the Aug 20 webinar theme [A-5].

[Heading 1] 38. Open-Source Strategy
[Normal] Open-source strategy is a strategic moat decision, not a generosity decision. The right open-source posture attracts developers (who contribute adapters, MCP servers, edge-case test cases), attracts users (who try the open-source version and convert to paid), and creates ecosystem lock-in ethically (the open-source primitives become the standard, but the proprietary data retains the value). DenialDefender's open-source strategy follows the "open primitives, closed data" model that MongoDB, Elastic, and Confluent used successfully (with their own governance lessons).
[Heading 2] 38.1 What Should Be Open-Source
[Normal] Three categories of artifacts are open-sourced under Apache 2.0. First, the agent orchestration framework adapters — the ADK 2.0 GraphWorkflow definition, the SequentialAgent / ParallelAgent / LoopAgent patterns DenialDefender uses, and the wrapper code that integrates ADK with GEAP components. These are useful primitives for any developer building multi-agent fleets on Google Cloud, not just healthcare-specific. Open-sourcing them establishes DenialDefender as a reference architecture for the broader Google agentic ecosystem. Second, the MCP tool servers — the payer-policy lookup MCP server, the medical-record structuring MCP server, the deadline-tracking MCP server. These are useful MCP servers for any healthcare-adjacent agent project. Open-sourcing them contributes to the MCP ecosystem and signals Google's open-standards posture (MCP is Anthropic-led, Google-supported per Phase B). Third, the synthetic denial letter dataset — 50-100 fully synthetic de-identified denial letters covering the top 5 payers × 10 denial types, with human-labeled expected outputs. This is a research-grade dataset that academic researchers, other hackathon teams, and competitors can use; it establishes DenialDefender as the canonical benchmark for denial-appeals AI. All three categories are Apache 2.0 licensed, with a CONTRIBUTING.md and a clear governance model (maintainers from the DenialDefender team, external contributions welcome via PR).
[Heading 2] 38.2 What Should Remain Proprietary
[Normal] Three categories of artifacts remain proprietary. First, the curated payer policy corpus — the ~4,000-clause curated corpus of top 20 payers' appeal policies, denial codes, submission requirements, and historical changes. This corpus is 6-12 months of legal and clinical curation work; open-sourcing it would give competitors a 6-month head start. The corpus is exposed via API (paid tiers get full access; free tier gets sample clauses) but never as raw data dumps. Second, the appeal outcome learning data — the corpus of recorded appeal outcomes (win/loss × payer × denial type × winning argument). This is the data moat (Section 36.4); open-sourcing it would destroy the moat. The Outcome Learning Agent's weights are exposed via API (the insights panel) but never as raw outcome data. Third, the Gemma fine-tune — the fine-tuned Gemma 4B model for appeal letter tone matching. The fine-tune is trained on proprietary appeal letter exemplars; open-sourcing the weights would expose the training data indirectly. The Gemma fine-tune is served via Vertex AI Model Garden; access is via the API only.
[Heading 2] 38.3 What Becomes an Ecosystem Primitive
[Normal] The "medical insurance appeals agent reference architecture" becomes an ecosystem primitive — a canonical pattern that other developers can build on. The reference architecture consists of: (a) the 8-agent fleet topology (Patient Advocate → Denial Triage → Policy Research → Evidence Assembly → Letter Drafting → Quality Review → Deadline Tracker → Outcome Learning); (b) the ADK 2.0 GraphWorkflow definition with Sequential / Parallel / Loop / Collaborative patterns; (c) the 5-tier memory architecture (Firestore session + pgvector semantic + Memory Bank procedural + temporal deadline + outcome learning); (d) the 2-HITL-gate pattern (triage confirmation + letter approval); (e) the 3-tier fallback strategy (live / degraded / demo-safe). Other developers building healthcare-AI agents (prior auth, eligibility, claim scrubbing) can fork the reference architecture and adapt it to their workflow — this is the "attracts developers" play. The reference architecture is documented in docs/ARCHITECTURE.md and licensed Apache 2.0.
[Heading 2] 38.4 What Attracts Developers
[Normal] Three things attract developers to contribute. First, the reference architecture — any developer building a multi-agent fleet on Google Cloud can study DenialDefender's architecture and learn from it. This is the "documentation as marketing" play. Second, the MCP servers — developers building healthcare-adjacent agents can use DenialDefender's MCP servers directly, contributing edge-case test cases and bug fixes. Third, the synthetic dataset — academic researchers studying healthcare AI can use the dataset as a benchmark, citing DenialDefender in their papers. Each developer contribution strengthens the open-source primitives without weakening the proprietary moat — developers contribute to the orchestration patterns, not to the policy corpus or outcome data.
[Heading 2] 38.5 What Attracts Users
[Normal] Users (patients, advocates, clinics) are attracted by the working product, not by the open-source code. The open-source primitives attract developers; the proprietary product attracts users. The free tier (1 appeal/month, watermarked) is the user acquisition play; the open-source repo is the developer acquisition play. Both feed the same funnel: free-tier users contribute outcome data (strengthening the moat); developer contributors strengthen the primitives (improving the reference architecture). The two funnels are complementary, not competitive.
[Heading 2] 38.6 What Creates Ecosystem Lock-in Ethically
[Normal] Ethical ecosystem lock-in comes from being the best, not from being closed. DenialDefender's open-source primitives are the canonical patterns; once other developers build on them, switching costs emerge (their code is coupled to the patterns). The proprietary data (corpus + outcomes) is the value that the open-source primitives point to — developers who build on the reference architecture will want to integrate with the proprietary corpus via API, not re-curate it. This is the same lock-in model that Stripe (open API spec, proprietary payments rails) and Twilio (open SDKs, proprietary telephony) used. It is ethical because the open-source primitives are genuinely useful without the proprietary data; the proprietary data is genuinely valuable without the open-source primitives; together they are more valuable than either alone. A competitor can fork the open-source primitives, but they cannot fork the outcome data — and without the outcome data, their product is structurally inferior.
[Heading 2] 38.7 Licensing Decision — Apache 2.0, Not GPL
[Normal] Apache 2.0 is chosen over GPL or AGPL because: (a) Google's own open-source agent frameworks (ADK, Gemma) are Apache 2.0, and consistency signals alignment; (b) Apache 2.0 permits commercial use without copyleft contamination, encouraging enterprise adoption; (c) AGPL would discourage enterprise adoption (the SaaS loophole closure is perceived as risky by enterprise legal teams); (d) the moat is data, not code — protecting the code via copyleft is unnecessary. The proprietary components (corpus, outcome data, Gemma fine-tune) are not licensed at all; they are served via API under a commercial terms-of-service.
[Heading 2] 38.8 Governance
[Normal] The open-source repo is governed by the DenialDefender team (post-hackathon, the incorporated entity). Maintainers review PRs; significant changes require maintainer consensus. A CONTRIBUTING.md documents the process. The repo is hosted at github.com/denialdefender/denialdefender (placeholder; actual repo TBD). A CODE_OF_CONDUCT.md (Contributor Covenant 2.1) is included. The open-source strategy is a post-hackathon 6-month execution priority; the hackathon submission itself is open-source from day one (judges can read the code), but the formal governance and contributor outreach happens after submission.
