  2551→

  2555→

  2559→
  2560→
  2561→## 29.1 Cloud Run Services
  2562→
  2563→DenialDefender deploys 4 Cloud Run services, not 8 (one per agent is over-engineering for the hackathon scale). The 4 services are: (1) denialdefender-api — the API Gateway + ADK orchestrator running all 8 agents in-process (single shared service for simplicity, scale-to-zero, faster dev cycle); (2) denialdefender-mcp — the MCP server exposure (separate service for isolation and independent scaling); (3) denialdefender-frontend — Next.js frontend served via Cloud Run or Firebase Hosting; (4) denialdefender-worker — async worker consuming Pub/Sub events for Outcome Learning and Deadline Tracker (separate service to isolate long-running work from request-response path). Justification: Cloud Run's per-service concurrency (configurable, default 80) handles the demo's traffic; one service per agent would add 8 deploy artifacts with no isolation benefit since agents share the same ADK process anyway. Phase B is explicit that Cloud Run is sufficient for hackathon-scale workloads [B-7].
  2564→
  2565→## 29.2 Firestore
  2566→
  2567→Firestore (Native mode) stores session state, case state, HITL approvals, deadline events, and learning update audit trail. Collections: patients, cases, denial_letters, appeal_letters, medical_records, outcomes (metadata only; embeddings in pgvector), deadline_events, learning_updates. Security rules enforce clinic isolation: request.auth.token.clinic_id == resource.data.clinic_id for clinic-tier reads/writes; guest cases have no clinic_id and are TTL'd. Real-time onSnapshot listeners drive the live UI. Firestore's free tier (50K reads, 20K writes, 1GB storage per day) is sufficient for the demo; cost beyond free tier is sub-dollar for 100 demo appeals.
  2568→
  2569→## 29.3 Cloud SQL pgvector
  2570→
  2571→Cloud SQL for PostgreSQL with the pgvector extension stores two tables: payer_policy_embeddings (semantic memory — ~100 rows for 3 payers × 5 denial types × ~7 clauses each) and outcome_embeddings (outcome corpus — 50 seeded synthetic outcomes + real outcomes over time). HNSW index for ANN. Connection pooling via Cloud SQL Connector (Python). IAM-based auth (no passwords in env vars). Cloud SQL's minimum cost is ~$30/month for a db-g1-small instance; for the hackathon, this is the largest single line item but well within the $150 GCP credit. The instance is set to scale-to-zero off-hours via scheduling where possible (Cloud SQL doesn't natively scale to zero, but can be stopped manually post-demo).

Each topic has at least one subscription; topics are clinic-scoped via message attributes for isolation. Pub/Sub's free tier (10GB/month data volume) is far beyond the demo's needs.

  2641→
  2642→DenialDefender's UX is multimodal in three senses. First, input modality: text (chat), file (PDF/image upload), structured (CSV bulk upload for clinic).   2769→## 31.8 Error Handling
  2770→
  2771→Errors are categorized into four classes with distinct handling. Retryable transient errors (Gemini 429, Cloud SQL connection blip, Pub/Sub timeout) retry with exponential backoff (3 attempts, jitter, max 10s). Schema validation errors (model returned malformed JSON) retry with a stricter prompt; if still failing, fall back to deterministic output for that agent. Domain errors (denial letter unreadable, no matching payer policy, missing medical records) surface to the user via the Patient Advocate chat with a clear next action; the pipeline pauses at the appropriate HITL gate rather than failing. Catastrophic errors (Gemini fully down, Cloud SQL unreachable) trigger the demo-safe path with a visible UI banner per Section 28. Every error is logged with correlation_id, agent_name, error_class, and stack_trace. The user never sees a raw stack trace; they see a humanized message + a "Show technical details" expander.
